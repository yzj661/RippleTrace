# 涟漪 RippleTrace — 技术选型与架构

---

## 1. 为什么是这个方向

### 1.1 与"通用大模型读代码"的本质区别

| 维度 | 通用大模型（Copilot / Cursor / ChatGPT） | 涟漪 RippleTrace |
|---|---|---|
| 输入 | 你贴给它的一段代码 | 整个仓库的调用结构 |
| 能力 | 语义理解、建议、生成 | **项目级结构推理** |
| 回答"改这个函数会影响谁" | 只能靠上下文猜，容易漏、无法验证 | 反向可达性遍历，**每条结论带调用链证据** |
| 正确性 | 不可量化 | 可对照编译错误 / 测试失败验证 |
| 规模 | 受上下文窗口限制 | 图遍历与仓库规模近线性 |

大模型很强，但它**看不见项目级结构**。涟漪 RippleTrace 正好补这个位。

### 1.2 为什么用 C++

1. **目标用户就是 C++ 团队**——银行、游戏、嵌入式、工业软件，这些领域最缺这类工具，也最不敢乱改底层代码
2. **性能**：调用图构建需要对每个 TU 做词法扫描。C++ 让"扫 10 万行代码"是秒级而不是分钟级
3. **部署**：单个无依赖 `.exe`，可直接进 CI，无需 Python/Node 运行时
4. **技术含量**：C++ 项目在评审中天然体现工程能力

## 3. 关键算法

### 3.1 函数提取（token + 花括号扫描）

不用正则，也不写完整 C++ 前端，而是：

1. 词法分析：剥离注释 / 字符串 / 预处理指令，产出 token 流
2. 遇 `{` 时判断它是否开启函数体：
   - 前面必须是 `)`，并向前配对出 `(`（支持多行签名）
   - 排除控制语句（`if/for/while/switch/catch`）
   - 排除**宏调用**：`TB_CASE("name")` 这类形参以字符串字面量开头，声明器不可能这样
   - 排除**构造函数初始化列表**：`Foo::Foo(int) : a_(x) {` 中 `a_` 前的 token 是 `:` 或 `,`
   - 排除**聚合初始化** / 类型定义（`class/struct/namespace` 引入符）
3. 记录函数体行范围（用于补丁归属），跨行扫描时用花括号深度跟踪

### 3.2 调用点解析（名称解析）

C++ 有命名空间、类作用域、重载，裸名无法直接定位。采用**作用域链候选**策略：

```
caller = tinybank::UserService::add_from_record
callee = "trim"
候选顺序：
  trim
  tinybank::trim
  tinybank::UserService::trim
  ...
全局唯一短名回退：若全仓库只有一个 trim，则解析到它
歧义（多个同名）→ 不解析，计入未解析并披露
```

**宁可漏，不可错**：把不确定的边丢掉并声明"结果是下界"，比错误连边更有价值。

### 3.3 影响面计算

```
输入：变更函数集合 C
1. 把 C 全部入队，dist=0
2. BFS 沿**反向边**（callersOf）扩展，parent[v] = 通往变更点的下一步
3. dist ≤ maxDepth 的所有节点 = 受影响集合
4. 由 parent 回溯重建每个节点到变更点的最短路径  ← "为什么"的证据
```

复杂度 `O(V + E)`，10 万行级仓库为秒级。

### 3.4 风险评分

```
score = 扇入分 + 距离分 + 公有面分 + 入口分 + 低层工具分 + 无测试覆盖分

扇入     ≥8 → +30   ≥4 → +22   ≥2 → +12   1 → +4
距离     1 跳 → +28  2 跳 → +16  3 跳 → +8  更远 → +3
公有头文件定义            → +20
入口点 (main / 测试)      → +12
小函数 + 高复用           → +8
无任何测试路径可达        → +14
```

分级：≥70 CRITICAL，≥50 HIGH，≥30 MEDIUM，其余 LOW。
**每个因子都写进 reasons 数组**，报告里可见——评分不是黑盒。

### 3.5 测试覆盖判定

先从所有测试函数出发做一次**正向** BFS，得到"测试可达集合"，
再判断受影响函数是否在其中。这样"无测试覆盖"这个高风险信号才是可靠的。

### 3.6 补丁归属（旧文件行号）

这是实现中最容易出错的一环，值得单独说明：

- 补丁 hunk 的新增行号是**补丁后**坐标，而当前工作树是**补丁前**版本
- 若直接拿新坐标去比函数体范围，插在函数上方的代码会让行号整体下移 → 归属错位
- 解法：解析时维护 `oldPos = newLine - netAdded + netRemoved`，输出**旧侧**范围用于归属
- 相邻函数间的间隙**按中点切分**，保证一行只归一个函数

实测：`changes.patch` 改 `trim()` → 精确识别出 1 个变更函数（早期版本误报 2–3 个）。

## 4. 技术栈

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | **C++17** | 结构化绑定、`std::optional`、`filesystem`；兼顾可移植性 |
| 编译器（已验证） | **MSVC 14.51**（VS 2026 Community） | 完整 C++17；`build.bat` 自动定位 vcvars |
| 备选编译器 | GCC / Clang（CMakeLists 已备） | 跨平台 |
| 文件系统 | `std::filesystem` | 标准库，无依赖 |
| 解析 | 自研 tokenizer + 花括号扫描 | **零第三方依赖**，任意环境可构建 |
| 升级路径 | `libclang` 实现 `IRepoParser` | 接口已预留，分析层零改动 |
| 输出 | 自研 JSON / DOT 序列化 | 避免引入 JSON 库 |
| 构建 | `build.bat` + `CMakeLists.txt` | 一键 / 跨平台双通道 |

**核心工程决策：零第三方依赖。**
原因：评审现场可能无法联网装包；而"能在任何 Windows 机器上 `build.bat` 一次通过"
本身就是一个可演示的工程指标。

## 5. 代码结构

```
RippleTrace/
├── build.bat                  一键构建（自动定位 MSVC）
├── CMakeLists.txt             跨平台备选
├── src/
│   ├── tokenizer.h/.cpp       词法分析，去注释/字符串/预处理
│   ├── parser.h/.cpp          函数与调用点提取（IRepoParser 接口）
│   ├── graph.h/.cpp           调用图 + 作用域链名称解析
│   ├── impact.h/.cpp          反向 BFS / 风险评分 / 测试选择 / 冲突检测
│   ├── diff.h/.cpp            unified diff 解析 + 旧侧行号归属
│   ├── repo.h/.cpp            文件发现与读取
│   ├── report.h/.cpp          文本 / JSON / DOT 渲染
│   └── main.cpp               CLI
├── samples/tinybank/          演示用目标仓库（27 文件，70 函数，22 测试）
│   ├── include/tinybank/      8 个公有头文件
│   ├── src/                   9 个实现文件，分 5 个层次
│   ├── tests/                 测试套件
│   └── changes.patch          演示用补丁（改底层 trim()）
└── docs/                      功能清单 / 技术选型 / 演示脚本 / Web版说明
```

**代码规模**：约 2 500 行 C++（8 个模块），演示目标仓库另有约 1 300 行。

## 7. 性能特征

| 阶段 | 复杂度 | 说明 |
|---|---|---|
| 词法分析 | O(N)，N = 字符数 | 单遍扫描 |
| 函数/调用点提取 | O(T)，T = token 数 | 线性 |
| 名称解析 | O(E × S)，S = 作用域链长 | 通常 S ≤ 4 |
| 影响面 BFS | **O(V + E)** | 图遍历 |
| 风险评分 | O(V log V) | 主要成本在排序 |

内存：整个调用图常驻，10 万行级仓库约数十 MB 量级。

## 8. 后续演进路线

| 阶段 | 目标 | 关键动作 |
|---|---|---|
| v0.2 | 提升解析精度 | 接入 libclang，实现 `LibclangParser`；用 USR 作为节点键 |
| v0.3 | 覆盖动态派发 | 虚函数调用保守传播 + 疑似虚调用标记 |
| v0.4 | CI 集成 | GitHub Action / Jenkins 插件，`--json` 驱动门禁 |
| v0.5 | **与 LLM 协同** | 静态图给出**精确影响集**，LLM 负责**解释每个受影响点该怎么改**——结构与语义分工 |
| v1.0 | 多语言 | tree-sitter 前端接入同一分析层 |

**v0.5 是真正有价值的一步**：不是用大模型替代静态分析，而是让静态分析给大模型
提供它自己算不出来的结构事实，再由大模型做语义解释。这才是"AI + 静态分析"的正确分工。
