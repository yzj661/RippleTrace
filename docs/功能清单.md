# 涟漪 RippleTrace — 完整功能清单

> **一句话**：输入「改了哪几行代码」，输出「谁会被影响、为什么、该重跑哪些测试」。
> 版本：concept build 0.1.0 ｜ 交付物：`build/RippleTrace.exe`
> 支持语言：**C++ / Java / Python** ｜ **零第三方依赖** ｜ Windows x64，静态链接 CRT

---

## 0. 这个工具做什么、不做什么

大模型（Copilot / Cursor / ChatGPT）很擅长"读代码、给建议"。**涟漪 RippleTrace 不重复做那件事。**

大模型看不见你的项目结构。你问它"我改了这个函数会影响谁"，它给不出可靠答案，你也无法验证。
涟漪 RippleTrace 做的是**结构推理**：

1. 构建整个仓库的**函数级调用图**；
2. 在图上做**反向可达性遍历**，得到变更的完整影响面；
3. 为每一条"受影响"的结论给出**带文件与行号的调用链证据**。

**分工是刻意的**：静态分析决定"哪些函数受影响、它们怎么连起来、危险程度怎么排序"——
这些是有确定答案的问题。大模型只回答一件它有优势的事：**每个受影响点上，人应该去核对什么**。
模型输出的每一个函数名都必须落在已算出的影响集里，否则整条建议被拒收（见 F11、F12）。

## 2. 功能详解

### F1 多语言仓库扫描与调用图构建 — `scan`

- **输入**：仓库根目录（可选限定语言）
- **识别扩展名**
  - C / C++：`.cpp .cc .cxx .c++ .hpp .hh .hxx .h .h++ .inl .ipp .tpp`
  - Java：`.java`
  - Python：`.py .pyw`
- **跳过目录**：`.git` `build` `out` `node_modules` `.vs` `cmake-build-debug`
  `cmake-build-release` `__pycache__` `target` `.idea` `venv` `.venv` `dist`
- **单文件上限**：4 MB
- **行为**
  - 逐文件词法分析 → 提取函数定义、函数体行范围、调用点、圈复杂度、行数
  - 跨文件解析调用边（作用域链 + 全局唯一名回退）
  - 输出统计：函数数 / 已解析边数 / 未解析调用点数 / 测试数 / 入口点数 /
    公有头文件定义数 / 歧义短名数
  - 输出 **Top 影响半径函数**排行（按直接扇入排序）——该仓库中"最不能随便改"的函数
- **命令**：`RippleTrace scan <repoDir> [--json <file>]`
- **实测**（`samples/tinybank`）：27 个源文件、**97 个函数、164 条已解析边、245 个未解析调用点、22 个测试**

**多语言是怎么做到的**：语言差异被收敛到一张 `LanguageProfile` 表里（作用域风格 `Brace`/`Indent`、
定义风格 `CppFunction`/`ClassMethod`/`PyDef`、注释与预处理语法、头文件判定规则），
解析器只按这张表取参数。分析层（建图、遍历、评分、渲染）**一行代码都不区分语言**。
因此新增一种语言 = 新增一张 profile，而不是改一遍算法。

### F2 变更影响面分析 — `impact`

- **输入**：一个或多个函数名（短名或限定名，支持重复 `--fn`）
- **行为**
  - 名称解析：精确限定名 → 短名唯一匹配 → 后缀匹配；**歧义时全部返回并显式列出**，不静默择一
  - 从变更函数出发做**反向 BFS**（O(V+E)），`parent[]` 记录每一步朝向变更点的下一跳，
    回溯即得**最短调用链**
  - 按风险评分排序输出，每条附风险成因
- **命令**：`RippleTrace impact <repoDir> --fn <name> [--fn <name>...] [--max-depth N]`
- **实测**：`--fn sha256_hex` → **影响 17 个函数、最大深度 4、0 严重 / 0 高 / 10 中 / 7 低、推荐重跑 11 个测试**

### F3 从补丁自动推导变更集 — `diff`

- **输入**：unified diff（`git diff` 输出），文件或文本
- **行为**
  - 解析 hunk，得到每个**连续新增行组**的范围
  - 把新增行归属到函数：行在函数体内 → 归该函数；行在函数签名的紧邻上方间隙 → 归其后那个函数
  - 相邻函数之间的间隙**按中点切分**，保证一个函数不会抢到另一个函数的行
  - 兼容空行上下文（空上下文行不会中断 hunk）
- **命令**：`RippleTrace diff <repoDir> --diff <patchFile>`
- **关键设计：归属使用旧文件行号。** 工具分析的是当前工作树（通常是补丁前的版本），
  而补丁 hunk 里的新增行号是补丁后的坐标。若直接用新坐标，插在函数上方的代码会把行号整体下移，
  导致归属错位。归属时按 `oldPos = newLine - netAdded + netRemoved` 换算回旧侧。
- **实测**：`samples/tinybank/changes.patch`（`trim()` 的性能优化，`+10 -2`）→
  精确识别出 **1 个变更函数 `trim`** → 影响 18 个函数 / 3 层 / 10 个测试

### F4 测试选择（推荐重跑清单）— `tests`

- **行为**：先从每个测试函数出发做**正向 BFS**，得到"测试可达集"；
  再检查影响面中的函数是否落在该集合里
- **命令**：`RippleTrace tests <repoDir> --fn <name>` 或 `impact ... --test-list <file>`
- **输出**：可直接喂给 CI 的清单，一行一个，按到达变更点的跳数升序
- **额外作用**：影响面中**不在**测试可达集里的函数会被标注 `no test path reaches this change`，
  并在风险评分里 +14 —— **没有测试保护的改动更危险**，这是评分模型里唯一一项"因为缺证据而加分"的因子
- **实测**：`--fn sha256_hex` → 11 个测试

### F5 可解释风险评分与分级排序

分值 0–100（超过则截断），全部因子都可在报告里逐条看到：

| 因子 | 触发条件 | 分值 |
|---|---|---|
| 扇入 | ≥8 个直接调用者 / ≥4 / ≥2 / =1 | +30 / +22 / +12 / +4 |
| 距离 | 距变更点 1 跳 / 2 跳 / 3 跳 / 更远 | +28 / +16 / +8 / +3 |
| 公有面 | 定义在公有头文件里（对外可见） | +20 |
| 入口点 | 程序入口 / 测试入口 | +12 |
| 小工具被广泛复用 | 行数 ≤15 且圈复杂度 ≤3 且扇入 ≥3 | +8 |
| **无测试保护** | 没有任何测试路径能到达它 | **+14** |

| 等级 | 分值 | 含义 |
|---|---|---|
| CRITICAL | ≥70 | 公有面 + 高扇入 + 近距，改动需双人复核 |
| HIGH | ≥50 | 影响面中等偏大 |
| MEDIUM | ≥30 | 需回读相关代码 |
| LOW | <30 | 通常可安全通过 |

**在真实第三方项目上观察到的现象**：最危险的不是最长最复杂的函数，
而是那些**只有 4 行的底层工具函数**（`gotoXY` 扇入 8）。它们被所有人调用、
改动代价被低估、且常常没有测试。这正是本评分模型想暴露的东西。

### F6 调用链证据（"为什么受影响"）

对每个受影响函数，输出从它到变更点的**最短调用链**：

```
Why (shortest call path change -> impact)
  [MEDIUM] AuditLog::record -> audit_fingerprint -> sha256_hex
  [LOW]    test_reconciliation_report -> build_reconciliation
           -> AuditLog::chain_digest -> sha256_hex
```

这条链不是猜测：每一步都是调用图中已解析的一条边，且带文件与行号。
**结论可核对，是这套工具与大模型"建议"的根本区别。**

### F7 变更交互冲突检测

一次提交改了多个函数时，检测它们是否**不能独立验证**：

- **直接依赖**：一个变更函数调用另一个变更函数
- **共同调用者**：两者被同一个调用者共同依赖

报告会写明冲突双方与共同调用者。**意义**：这类改动看起来是两处独立修改，
实际上必须一起验证——漏掉这一点会让"改完各自跑一下测试"这种流程失效。

- **实测**：`--fn trim --fn to_lower` → 检出一对交互

### F8 未解析调用点与歧义披露（宁可漏，不可错）

- **名称解析只在确定时连边**。歧义短名不解析，计入未解析并在报告里披露
- 报告的 Limitations 段会写明："本仓库有 N 个调用点无法解析到定义（外部库、模板或歧义重载）；
  这些边已从影响集中排除，**因此结果是下界**"
- **理由**：错误的影响面比不完整的影响面更危险——前者会让你以为安全，从而跳过本该做的检查

### F9 跨语言边拒绝与语言隔离

同一个仓库里有多种语言时（例如 C++ 主程序 + Python 脚本 + Java 服务），
短名会跨语言撞车（三个语言都定义 `main`）。

- 每个函数带语言标签，同名冲突时加后缀区分（`main@cpp` / `main@python`），边随节点一起改名
- **默认拒绝跨语言调用边**（`allowCrossLanguage = false`）
- **为什么这不是"保守"，而是"正确"**：实测在一个混合仓库上，跨语言边 26 条 **全部是假的**
  （C++ 的 `find_value` 连到了 Java 的 `find`）。真实的跨语言调用走 FFI / JNI / socket / 子进程，
  本来就不会表现为一次直接调用。让它们进图只会污染影响集
- 需要时可用 `--allow-cross-language` 显式打开

### F10 四种输出格式

| 格式 | 开关 | 用途 |
|---|---|---|
| 控制台彩色报告 | 默认 / `--no-color` | 人读，风险分级着色 |
| JSON | `--json <file\|->` | CI 门禁、IDE 插件、二次消费 |
| Graphviz DOT | `--dot <file\|->` | 影响子图可视化（`dot -Tsvg`）；**仅 `impact` / `diff`** |
| 测试清单 | `--test-list <file\|->` | 直接喂给测试运行器；**仅 `impact` / `diff` / `tests`** |

`--quiet` 为静默模式：只产出文件，不打印报告。`--print-prompt` 打印即将发给大模型的完整提示词（见 F11）。

**不适用于当前子命令的开关会被拒绝，而不是被静默忽略。** 例如 `scan` 还没有变更集，
所以 `scan --dot` / `--test-list` / `--fn` / `--ai` 一律报错并 **exit 2**，
而不是安静地不产出任何文件——**一个悄悄什么都没写的开关，比一个直接报错的开关更难排查。**

### F11 AI 解释层（接地式核查建议）— `--ai`

**这是"静态分析 + 大模型"的分工实现。**

- **静态分析给出的事实**（放进提示词的 FACTS 段）：变更了哪些函数、影响集里有哪些函数、
  每个点被影响的**原因**、它与变更点的**调用链**、风险分与风险成因、哪些测试能覆盖它、
  有多少调用点没解析出来
- **大模型只被问一件事**：在这个点上，人应该**去核对什么**、以及**为什么这件事重要**
- **输出结构**：一段总体说明 + 若干条建议点，每条含
  `function` / `priority` / `what_to_check` / `why_it_matters`
- **可检查性**：`RippleTrace prompt <repo> --fn <name>` 或 `--print-prompt`
  会打印**与真实请求完全一致**的提示词（同一个 `buildSystemPrompt()`），不需要调用模型就能审查
- **失败不影响分析**：模型不可用时，完整的静态分析结果照常输出，AI 段只给出失败原因。
  **AI 是可选增强，不是单点依赖**

### F12 接地性强制（编造即拒收）

模型返回的**每一个**函数 id 都必须落在"计算出的影响集 ∪ 变更集"里，否则该条建议被拒收。

- 拒收不是静默丢弃：报告会列出被拒的条目和拒收原因
- 实测：`tools/fake_llm_server.py` 是一个**故意返回错误内容**的假模型端点，
  它给出 2 条合法 + 2 条编造的建议 → 输出
  `grounding: impact set is authoritative; 2 point(s) kept, 2 rejected`，
  并逐条说明 `it exists in the repository but is NOT in the computed impact set`
- 实现细节：`enforceGrounding()` **只做过滤，不重排**——
  排序是模型按重要性给出的，重排会破坏它

**为什么这一条最重要**：它把"大模型可能编造"从**风险**变成了**已处理的失败模式**。
你不需要相信模型，你只需要检查它有没有越界——而这件事是程序做的。

### F13 AI 配置与密钥安全

- **配置来源与优先级**：环境变量 > `rippletrace.env` > `.env`
- **查找位置**（按顺序）：`rippletrace.env` / `.env` / `../rippletrace.env` / `../.env` /
  `build/rippletrace.env` / `build/.env` / `<根>/rippletrace.env` / `<根>/.env`
  —— 配置文件放在 **exe 旁边**或**项目根目录**都能被读到
- **键名**：`RIPPLETRACE_AI_KEY` / `_ENDPOINT` / `_MODEL` / `_LANG`，
  也可用 `--ai-key` / `--ai-endpoint` / `--ai-model` / `--ai-lang` 覆盖
- **无需重启**：服务在 AI 未启用时**每次请求都重读配置**。
  启动之后才发现没配 key 的用户，创建文件再点一次按钮就行
- **密钥安全（三条硬约束）**
  1. 密钥只从**服务端**读取（环境变量或配置文件），**前端永远拿不到**
  2. `/api/explain` **不接受**浏览器传入的任何密钥
  3. `/api/health` 的响应里**不能出现密钥**——自动化测试会断言响应中不含 `sk-` / `apikey`
- **三层传输**（按顺序尝试，全部失败才报错）
  1. WinHTTP 直连（强制 IPv4）
  2. WinHTTP + 系统代理
  3. 子进程 helper `tools/llm_transport.py`——**密钥通过 stdin 传入，绝不出现在命令行参数里**
     （命令行参数在同机其他进程里可见）
- **无 key 也允许**：不带 key 请求**本地端点**（Ollama / llama.cpp）是合法用法。
  这种情况下失败信息会明确写"没有配置 API key"，而不是甩一堆 TLS 错误码

### F14 回答语言可选 — `--ai-lang`

- 取值：`zh`（默认，简体中文）/ `en`（English）/ `auto`（跟随提问语言，默认回落到英文）
- 未知取值一律回落到 `zh`；取值解析在 `-_ ` 处切分主标签后**精确匹配**，
  所以 `enterprise` 不会被当成 English
- **标识符永远不翻译**：函数名、文件路径、行号、API 名一律保持 FACTS 段里的原样。
  翻掉它们，引用就无法核对了
- 对比实测：`--ai-lang zh` 的输出含中文；`--ai-lang en` 的输出 **CJK 字符数为 0**

### F15 Web 图形界面 — `serve`

- **命令**：`RippleTrace serve <rootDir> [--port 8080]`，启动后打印 URL
- **零第三方依赖**：HTTP 服务用原生 winsock 实现，前端是**一个自包含 HTML 文件**（1 083 行）
- **界面元素**
  - 统计卡片：函数数 / 调用边 / 未解析调用点 / 测试数 / 入口点 / 歧义短名
  - 影响半径排行表（**点击任意一行即可分析该函数**）
  - **分层影响面图**：SVG 绘制，左侧为变更点，向右按调用深度逐层展开调用者；
    节点按风险着色，边为调用关系。点击节点高亮它的调用链
  - **五个结果标签页**：受影响函数（含成因与调用链）/ 测试 / 变更交互 / **AI 核查建议** / 局限说明
  - AI 状态横幅：显示是否启用、模型名、回答语言、密钥来源
- **默认行为**：若沙箱根目录下有 `samples/tinybank`，页面提供"载入演示仓库"按钮；
  否则路径框回落到 `"."`
- **实测**：`sha256_hex` → 17 个受影响函数，分 5 层

### F16 HTTP JSON API

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/health` | 健康检查；含 `tool` / `version` / `hasSamples` / `sandboxRoot` / `ai.enabled` / `ai.keySource` / `ai.language` / `ai.helperAvailable` / `ai.configCandidates` |
| GET | `/api/scan?path=<dir>` | 扫描并返回统计 + 函数列表 + 影响半径排行 |
| POST | `/api/impact` | 影响面分析，body `{"path":"...","fn":["a","b"]}`，可选 `maxDepth` |
| POST | `/api/diff` | 补丁驱动分析，body `{"path":"...","patch":"x.patch"}` 或 `patchText` |
| POST | `/api/explain` | AI 核查建议，body `{"path":"..."}` |

- 返回的 `layers` 字段是**按深度分好组**的节点，前端因此不需要自己算布局
- **`/api/explain` 有刻意的守卫**：没先跑过一次 impact 就调用，会返回
  `run an impact analysis first: the explanation is validated against the impact set that analysis produced`
  —— 接地性验证需要一份真实的影响集作为依据
- POST 的 `path` 也接受相对路径，按沙箱根目录解析

### F17 分析沙箱与请求限流

- 启动时必须指定一个根目录，**所有分析请求只能指向该目录内部**
- 越权路径返回 `403` 并说明原因，而不是静默失败
  - 路径比较**对分隔符不敏感**（`\` 与 `/` 等价），避免同一目录因写法不同被误判
  - 已回归验证：`C:\Windows` → 403，`..\..\..` → 403，沙箱根目录的父目录 → 403
- 服务默认只监听 `127.0.0.1`（回环），不是 `0.0.0.0`
- 请求体上限 **32 MB**，请求头读取上限 64 KB，套接字收发超时 **15 秒**
- **意义**：一个能读取任意路径、且暴露给局域网的本地 HTTP 服务是危险的默认配置。
  这些限制让"演示给别人看"这件事变得可以放心

### F18 源码编码健壮性

真实项目里的源文件编码是混乱的。实测的第三方 C++ 项目里同时存在
UTF-8 BOM、UTF-8 无 BOM、和 GBK 三种源文件。

- **读取顺序**：严格 UTF-8 校验 → 系统 ANSI → 936（GBK）→ 1252 → 全失败则逐字节替换为 U+FFFD
- **为什么不能只看"是不是合法 UTF-8"**：GBK 的双字节序列**经常本身就是合法 UTF-8**
  （这正是最初的漏洞——GBK 文件通过了校验，中文注释被解成代理项，
  发给模型后变成 `HTTP 400: lone leading surrogate in hex escape`）
- **严格 UTF-8 校验 + 净化**（`src/utf8.{h,cpp}`）：拒绝代理项（`ED A0 80`–`ED BF BF`）、
  过长编码（`E0 80`–`E0 9F`、`F0 80`–`F0 8F`）、超出 U+10FFFF（`F4 90`–`F4 BF`）、
  截断序列、孤立续字节、`C0`/`C1`/`F5`–`FF`；每段非法子序列替换为一个 U+FFFD
- **约定**：字节级分析本身不需要 UTF-8；但**任何进入提示词或报告的字符串必须是真 UTF-8**
- **命令行同样处理**：参数通过 `GetCommandLineW` 取宽字符再转 UTF-8，
  所以**中文路径**可用（`RippleTrace scan E:\我的项目`）
- 实测：项目内 99 个文本文件全部合法 UTF-8；第三方 GBK 文件的中文注释解码正确
  （`// 这是中文注释：颜色控制函数`），0 个 U+FFFD

### F19 Visual Studio 工程感知

**问题**：项目目录里常有"在磁盘上但没参与编译"的文件（备份副本、被排除的实验代码）。
把它们当活代码分析，报告会指向错误的文件——实测踩过：报告指向 `PrintMap main(1).cpp:73`，
而 `main(1).cpp` 根本不在 `.vcxproj` 里。

- **行为**：发现 `.vcxproj` 后，只分析它真正编译的文件（`ClCompile` / `ClInclude`）
- **透明**：扫描摘要会报告"发现工程文件 / 从工程取到 N 个文件 / 排除了 M 个不在构建中的文件"
- **可关闭**：`--include-non-build` 分析磁盘上的全部源文件
- **实测**：修正后报告正确指向 `main.cpp:200`

### F20 零依赖可复现构建

- **`build.bat`**：自动定位 `vcvars64.bat`，MSVC 一键构建，**首次即成功**
- **`CMakeLists.txt`**：跨平台备选（GCC / Clang）
- **零第三方依赖**：不用 CMake 拉包、不用 vcpkg、不用 NuGet。
  全部代码只依赖 Windows 自带库——`dumpbin /dependents build/RippleTrace.exe` 只有
  `KERNEL32.dll` / `SHELL32.dll` / `WS2_32.dll` / `WINHTTP.dll`
- **CRT 静态链接**：没有 `VCRUNTIME140.dll` / `MSVCP140.dll` 依赖，
  **收件人机器不需要安装 VC++ 运行库**
- **为什么把"零依赖"当功能而不是洁癖**：评测/答辩现场不保证有网络，
  "`build.bat` 在任何一台 Windows 上第一次就能构建成功"本身就是一项可演示的工程指标
- 单元测试：`tools\test.bat` → **179 项检查，0 失败**

## 5. 已知边界（诚实声明）

| 限制 | 说明 | 生产化路径 |
|---|---|---|
| 启发式解析 | 基于 token + 花括号 / 缩进扫描，不是完整编译器前端 | 换 `libclang` 实现 `IRepoParser`，**分析层零改动** |
| 非 C++ 语言 | Java / Python 走同一套启发式，不是各自语言的完整前端 | 每个语言各接一个 tree-sitter 语法，`IRepoParser` 接口不变 |
| 模板 / 重载 | 无法解析实例化与重载决议 | libclang AST + USR 作为节点键 |
| 虚函数 / 回调 | 动态派发路径不可见 | 增加"疑似虚调用"标记与保守传播 |
| 跨 TU 宏 | 宏展开后的调用点不可见 | 预处理后再分析 |
| 方法调用接收者 | 无法确定接收者类型，故 `obj.method()` 大量计入未解析 | 需要类型推导或语言服务器 |
| 非 UTF-8 源文件 | 按 UTF-8 → ANSI → 936 → 1252 顺序探测，全失败则替换为 U+FFFD | 读取 `.editorconfig` 的 charset 声明 |
| 大规模仓库 | 未做增量与并行 | 增量重解析 + 多线程 + 预编译头 |
| 大模型回答 | 模型仍可能给出无用建议（但不会给出**越界**建议，见 F12） | 更好的提示词与更强的模型 |

**关于"未解析调用点"的重要澄清**：本仓库自分析时 1 999 个调用点里只有 599 个解析成功，
但**绝大多数未解析项不是 `std::` 库调用**——其中 1 192 个是**裸标识符**
（`size` 211、`empty` 131、`push_back` 92、`find` 68…），即接收者类型无法推断的方法调用，
`std::` 限定的只有 187 个。这个数字说明的是**启发式方法调用的固有上限**，
没有任何粉饰的必要：**结果是下界，报告里写明了这一点。**

**这些限制不影响核心价值主张**：把静态图上的精确推理与大模型的语义理解结合起来，
而不是用大模型去猜结构。分析层（图遍历、风险评分、调用链重建）是确定性的且已验证正确，
不确定性全部集中在解析层——而解析层是可替换的。
